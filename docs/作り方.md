# 作り方

札幌市議会の会議録（2007〜2026年の本会議と委員会）を、話題ごと・区ごとに辿れる形にした工程の記録。工程1〜8と、年表、区の入口について、同じ4つの項目（やったこと、判断と理由、モデル、かかった時間）で書く。最後に、やってみてわかったことをまとめる。コマンドは [動かし方.md](動かし方.md)、全体の流れは [docs/README.md](README.md) にある。

数はどれも2026年11月19日のもの。

## 目的と、先に決めたこと

- 目的: 演説やブログを考えるときに、20年分の議会の話題を早く押さえる。会議録検索システムは会議1日分ずつ読むしかなく、話題ごとの流れがつかめない
- 範囲: 本会議（定例会・臨時会）と委員会の両方。具体的なやり取りの多くは予算・決算特別委員会と常任委員会にある。委員会の量は本会議のおよそ5倍
- 年数: 20年。統一地方選（2007, 2011, 2015, 2019, 2023年の4月）で任期を区切り、2007年5月からの5期
- 出典: 人前で使うので、すべての文に会議録へのリンクを付ける。AI が要約で間違えた数字や答弁をそのまま口にしないよう、数字と引用を原文と機械的に照合し、確かめられなかった文に印を付ける

最初に2つを決めた。

- **話題の一覧を先に固定する。** AI に話題を自由に付けさせると20年分でぶれる。分類の前に一覧を決め、AI はその中から選ぶだけにする。軸は「政策分野」と「地域（全市と10区）」の2つ
- **出典は記録の番号で書かせ、URL はコードで付ける。** AI には出典を記録の番号（`[246405-1]`）で書かせる。AI が URL を間違えることがなく、文中の数字や引用を、引いた記録と照合できる

## タスクの分け方

AI はコンテキストがいっぱいになるほど精度が落ちる。そこで、1つの作業を毎回まっさらなコンテキストで始められるように分けた。

- AI に生の会議録を大量に読ませない。取得、変換、分割、並べ替え、照合はコードでやる。AI の仕事は「1件読んで分類・要約する」（工程5）と「要約を束ねて経緯を書く」（工程6・7）の2種類だけ
- 状態は会話ではなくファイルに置く。各工程は「指示書と入力ファイルを読んで、出力ファイルを書く」で終わる。どこまで処理したかは出力のファイルでわかり、何度流しても済んだ分は飛ばす
- 大量の分類・要約は、API を呼ぶスクリプトで回す（Message Batches）。1回ごとに白紙から始まり、出力の JSON の形を API が保証する
- 束ねる作業は2段にする。まず「話題×任期（4年）」でまとめ、それを20年分つなぐ。1回に読む量を上限に収める
- AI のエージェント（Claude Code、Codex）でやるのは、スクリプトを書く・直す、指示書を作る、結果を確かめる、の3つ

API のスクリプトで回すか、Claude Code などのエージェントで回すかは、次のように比べて決めた。同じモデルなら能力は同じで、差が出るのは、数百〜数万回をそろった条件で回すときと、あとで検証するとき。

| | API のスクリプト | Claude Code などのエージェント |
|---|---|---|
| モデルが見るもの | 指示書とデータだけで、毎回同じ | エージェント自身の指示、ツールの説明、CLAUDE.md、それまでの会話。データは自分で読みに行く |
| 文脈 | 1回ごとに白紙 | 1つのセッションで続けると会話がたまり、途中で要約されて精度が落ちる |
| データを全部読むか | コードで渡すので、必ず全部読む | 大きいファイルは分けて読むことになり、読み飛ばすことがある |
| 出力の形 | JSON の形を API が保証し、コードで確かめられる | 頼んだとおりにファイルを書くが、形の保証はない |
| 再現性 | モデル、effort、指示書の版を記録に残せる | 条件をそろえにくい |
| 量 | バッチで数万件を回せる | 工程5は約7,400万トークンを読む。エージェントの利用上限に収まらない |

## 工程1 原本の取得

- **やったこと**: 札幌市議会会議録検索システムから、2007〜2026年の定例会・臨時会・委員会の会議録を、会議1日分ずつ取った（約3,500件）。Shift_JIS の HTML のまま `data/raw/` に置き、年×種別ごとの目録（会議名、日付、閲覧 URL、発言数）を作った
- **判断と理由**:
  - 2007年からにした。統一地方選の4月で任期を区切ると、ちょうど5期20年になる
  - リクエストは1.5秒に1回、並列にしない。相手のサーバーに負荷をかけないため
  - 取得済みのファイルは飛ばし、途中で止めても続きから再開できるようにした。一括だと長いので、6回に分けて流した
  - 原本は Git に入れない。容量が大きく、もう一度取れば作り直せる
- **モデル**: なし
- **かかった時間**: 約2時間（1回20分前後を6回）

会議録検索システムの仕組み（2026年11月15日に確かめた）:

| 用途 | パラメータ |
|---|---|
| 会議の一覧（1年分が1ページに出る。ページ送りはない） | `ACT=100&KGTP=<種別>&FYY=<年>&TYY=<年>` |
| 会議1日分の本文（全発言が1回で取れる） | `ACT=203&KENSAKU=0&SORT=0&KTYP=1,2,3,0&KGTP=<種別>&FYY=<年>&TYY=<年>&FINO=<ファイル番号>` |
| 人が読む閲覧画面（出典リンクに使う） | 一覧の各行にある `ACT=200&...&FINO=...` |
| 発言の位置で開く閲覧画面 | 上の URL から `UNID` を外し、`HUID=<発言ID>` を入れる（`lib.mjs` の `speechUrl`） |

- URL は `https://sapporo.gijiroku.com/voices/cgi/voiweb.exe`。文字コードは Shift_JIS
- 種別 `KGTP`: 1＝定例会、2＝臨時会、3＝委員会（常任委員会、予算・決算特別委員会、調査特別委員会、議会運営委員会など）
- 本文に `HATSUGENMODE=0` を付けると、最初の発言1件しか返らない。付けない
- 発言者の記号: ○＝議長・委員長、◆＝質問する議員、◎＝答弁する市長・局長など
- 件数の目安: 定例会が年に約26〜28日分（各回の「目次」を含む）、委員会が年に約140〜150日分
- 最新の会議は載るまで数か月かかる（2026年11月時点で、定例会は第2回の6月5日分まで）

## 工程2 Markdown への変換

- **やったこと**: 原本を UTF-8 の Markdown にした（`data/md/`）。各ファイルの頭に目録の情報（会議名、号、日付、種別、閲覧 URL、発言数）を付け、発言の前に `<!-- HUID12345 -->`（会議録システムの発言の番号）を置いた
- **判断と理由**:
  - 本文は書き換えない。タグを外して `<BR>` で行を分けるだけにし、行頭の全角空白（字下げ）も残す。あとで原文と照合するため
  - 変換のたびに、原本からタグを外した文字列と、Markdown から付け足した部分を除いた文字列が1文字残らず一致するかを確かめる（無損失）
  - 発言の番号（HUID）を残し、出典を発言単位で示せるようにした
- **モデル**: なし
- **かかった時間**: 数秒

## 工程3 構造化

- **やったこと**: 会議録を、発言、目次、会派の名簿、質問者ごとのまとまりに分けた。まとまりは21,055件（本会議3,390、委員会17,665）。工程5で AI が読む単位は、ここで作る。設計と結果の詳しいことは [工程3の設計.md](工程3の設計.md)
- **判断と理由**:
  - **本会議は、議長の指名でまとまりを区切った。** 議長がある議員を指名してから、次に別の議員を指名するまでを1人分のまとまりにする（休憩では区切らない）。札幌の代表質問は一括質問方式で、1人がたとえば9項目をまとめて聞き、市長、副市長、局長が「私からは7項目めについて」と分担して答える。どの答弁がどの項目への答えかは工程5の AI に対応づけさせるので、読む単位は「1人分の質問と、それへの全答弁」にした
  - 委員会は、委員長の発言（「次に、〜の質疑を行います」など）で議題を区切り、1つの議題の中の1人の委員の質疑と答弁を1つのまとまりにした。一問一答が多いが、同じ単位で1回の API 呼び出しに収まる
  - 目次（本会議と特別委員会にだけある）は、まとまりの区切りには使わず、大項目と照合にだけ使った
  - 会派の名簿（任期×氏名→会派）は手で直す CSV を本体にし、スクリプトは、札幌市議会の会派別名簿の過去の版（Wayback Machine）、本会議の出席議員の欄、会派を名乗った箇所と照らして確かめるだけにした
  - 文書質問は、質問と答弁書の本文が会議録にないので、まとまりにしない
- **モデル**: なし
- **かかった時間**: 全部で15秒ほど

## 工程4 話題の一覧

- **やったこと**: 代表質問の大項目（3,562件）と、委員会の議題（6,567件）を材料に、話題53個の一覧（`pipeline/topics.csv`）を作った。古い4年と新しい4年から種類ごとに抜いた300件を、工程5の最初の版の指示書で試しに分類し、その結果で一覧の分け目と指示書を直してから固定した
- **判断と理由**:

| 決めること | 決めたこと | 理由 |
|---|---|---|
| 細かさ | 雪、子育て、交通、地域の担い手、AI・デジタルの5分野は細かく（4〜6個ずつ、計25個）、ほかの分野は粗め（1〜5個ずつ、計27個）。受け皿の「その他」を足して53個 | よく使う分野ほど細かく引けるようにする。全体を細かくすると AI の仕分けがぶれ、粗すぎると使いにくい。細かく分ける5分野の分け方は、本文でキーワードが何件のまとまりに出るかを数えて決めた |
| 1つの項目に付ける話題の数 | 主1つ＋副0〜2つ | 2つの分野にかかる項目（「高齢者世帯の除雪支援」は除排雪と高齢者福祉、など）を、どちらからも探せるようにする |
| 副の話題の扱い | 年表には載せる。経緯の文章は主の話題でだけ書き、副の話題の README には「関連」として1行で触れる | 工程6・7で、AI が同じ話を2つの話題で二重に書かないようにする |
| 受け皿 | 一覧に「その他」を置く | 受け皿がないと、AI が近い話題に無理に押し込み、話題の中身が濁る。本番で「その他」は0.4% |
| 地域 | 政策分野とは別の軸として、すべての記録に付ける。一覧は「全市」と10区で固定する。全市の話の中で特定の区に具体的に触れたものは、全市と区の両方を付ける。区より細かい地名（あいの里、篠路駅など）は一覧にせず、会議録に出たとおりに別の欄（地名）に残す | 地域で絞れば、その区の話を分野をまたいで集められる。地名は固有名詞なので、自由に書かせてもぶれにくい |
| 記録の置き方 | 工程5の記録の本体は `records/<年>.jsonl` の1か所にだけ置き、Git で管理する。話題ごとの年表と区ごとの記録はコードでここから作る | 2つの話題に載る記録も中身は1件なので、片方だけ直して食い違うことがない。記録は API で作るので、なくさないようにする |
| 下書きの材料 | 代表質問の大項目と、常任委員会・調査特別委員会の議題 | 代表質問の大項目だけだと、委員会でしか出ない細かい話題が漏れる |

  - 下書きは、話題の候補をキーワードで振り分けるスクリプトを使い、どの候補にも入らなかった言い回しだけを読んで漏れを探して作った。材料の全部（約8.8万字）は AI に読ませていない
  - 試行の結果: 300件すべて記録できた（1,067項目）。「その他」は0.5%で、どの話題にも1件以上入った。数字2,151個はすべて原文にあり、引用1,531個のうち3個が語尾を言い切りに直していた。主の話題で迷った組み合わせのうち、両方向に出た6組（IT産業↔経済と雇用、生活道路の排雪↔除排雪の体制 など）は `topics.csv` の分け目を書き足した
  - 試行で決まりを2つ直した（指示書 v2）。地域は「全市」と区の両方を付けてよい（北区で絞ったときに拾えるように）。引用は語尾を直さない
  - 一覧を固定したあとに変えると、工程5から流し直しになる
- **モデル**: 試行は Opus 5.5（指示書 v1）
- **かかった時間**: 材料の取り出しは数秒。試行は300件をバッチで6分

## 工程5 分類・要約

- **やったこと**: まとまり1件ずつを API で読み、項目ごとの記録（話題の主・副、地域、地名、質問と答弁の要旨、数字、約束の原文の引用、発言の番号、出典の URL）を作った。読む候補19,212件（8,158万字）のうち18,981件から項目54,813件を作り、`records/<年>.jsonl` に置いた。残りの231件は手続きだけで項目なし（資料の配付の案内と「異議なし」だけ、など）
- **判断と理由**:
  - 年ごとに1つのバッチにして送り、形式チェックに落ちたものは2回まで送り直した
  - 出典は発言の番号（HUID）で持たせ、URL はコードで付けた
  - 「約束」の引用は語尾を直さず、原文どおりに写させた（工程8で原文と照合するため）
  - 委員会の一問一答を往復ごとに別の項目に分けすぎないよう、指示書 v3 で「同じ施策の一連のやり取りは1項目」「分け目に名前の出てくる話題の範囲も読み比べる」を足した
- **モデル**: Haiku 5.5、指示書 v3、effort medium、出力の上限64,000トークン。件数の多い工程は、費用と品質のバランスで軽いモデルにした。Haiku で3回とも形式チェックに落ちた4件は、Sonnet 5.5 で流し直した（記録の `model` でわかる）

工程4の試行と同じ300件を、3つのモデルで分類して比べた（`04c_compare_models.mjs`）。Opus の結果を基準にした。

| | Opus（指示書 v1、基準） | Sonnet（v2） | Haiku（v2） | Haiku（v2、effort high） | Haiku（v3） |
|---|---|---|---|---|---|
| 話題: 拾えた割合／当たった割合 | — | 87%／91% | 92%／83% | 94%／81% | 91%／82% |
| うち代表質問 | — | 94%／94% | 96%／93% | 97%／93% | 95%／93% |
| 委員会の質疑の項目数（Opus を1として） | 1 | 1.08 | 1.32 | 1.24 | 1.13 |
| 原文に見つからない数字／引用 | 0%／0.2% | 0.1%／0.2% | 0.5%／1.0% | 0.5%／1.2% | 0.4%／0.7% |

- 比べ方: 項目の分け方はモデルごとに違うので、まとまりごとに「付けた主の話題の集まり」を比べた。「拾えた割合」は Opus が付けた話題のうちそのモデルも付けた割合、「当たった割合」はそのモデルが付けた話題のうち Opus も付けた割合。項目を細かく分けるモデルは拾えた割合だけが高く出るので、両方を見る。Opus の結果も正解ではなく、あくまで基準
- Sonnet: 委員会の質疑と代表質問では Opus とほぼ同じ。弱いのは討論・説明・委員長報告で、補正予算への賛成討論を、Opus は12項目に分けたのに Sonnet は1項目にまとめた
- Haiku: 代表質問は Opus に近い。委員会の一問一答を往復ごとに別の項目に分け、分け目を読み違える（消防団を「防災と消防」に、など）。数字・引用のずれは、並んだ数字を1つにまとめた・語尾を直したものが多く、工程8で原文と照合すれば見つかる。effort high にしても当たった割合は変わらなかった
- 指示書 v3 で分けすぎがほぼ直り（地下鉄の安心車両の3往復が1項目に）、消防団も「地域の担い手」に入るようになった

- **かかった時間**: 約5時間（2026年11月17〜18日）。送り直しのバッチは、処理待ちで数時間かかることがある

## 工程6 話題×任期のまとめ

- **やったこと**: 話題×任期（4年）の265組について、工程5の記録を API で読み、その4年の経緯をまとめた（`bundles/<話題>/<任期>.json`、`.md`）。書く欄は5つ（この4年の要点、主な動き、会派ごとの主張、市の答弁の変化、残っている論点）
- **判断と理由**:
  - 読むのは主の話題の記録（工程5の要旨）だけ。原文は読まない。副の話題は年表にだけ載せる
  - 2003-2007 の任期（2007年1〜4月の記録だけ）は外す。年表には載せる
  - 1回に読む量は7.5万字までにした。超える組（265組のうち130組）は日付で時期に分けて時期ごとにまとめ、それを1つにまとめ直す（2段）
  - 出典は記録の番号で文ごとに書かせ、会議録の URL はコードで付ける
  - 形式チェックに落ちたもの（入力にない番号、出典のない文が1割を超える、同じ文が5回以上、主な動きが空、会派・答弁の変化・残る論点がすべて空）は自動で送り直し、2回落ちたものは Opus で流し直す
- **モデル**: 細かく分けた5分野の話題（125組）は Opus 5.5、ほかの分野の話題（140組）は Sonnet 5.5（2回落ちたものは Opus）。effort medium

本番の前に、7組（細かく分けた5分野から5つ、ほかから2つ。任期もばらした）で3つのモデルを比べた（`06b_compare_bundle.mjs`）。

| | Opus 5.5 | Sonnet 5.5 | Haiku 5.5 |
|---|---|---|---|
| 出典のない文 | 0% | 3.8% | 10.5% |
| 入力にない番号 | 0 | 1 | 0 |
| 数字: 引いた記録に見つからない | 1.1% | 2.4% | 1.4% |
| 引用: 約束の原文と一致 | 141/143 | 75/76 | 48/53 |
| 崩れ | なし | 1組 | なし |

- Opus: 文ごとに出典があり、議員名・会派・日付・金額・答弁の原文まで具体的。「市の答弁の変化」を原文付きで拾えた（除排雪で、2019年の「直ちに予算を増額するということにはつながらないものと考えております」から、2022年の「初冬期の大雪への対応を当初から一定程度想定して予算化していく考えであります」へ、など）
- Sonnet: 6組はまずまず。除排雪の組で、中身のない文（「以上である。」）を並べて終わり、会派・答弁の変化・残る論点が空になった
- Haiku: 流れはつかめるが、出典を段落の終わりにまとめて付けるので、どの文の根拠かがわからない。日付がぼやける（「2020年冬」など）
- 工程5では Haiku にしたが、工程6では差が大きく出た。工程6は「市の答弁が何年から変わったか」を拾う仕事で、分類より難しく、しかも工程5の要旨の上に積むので粗さが重なる。よく使う5分野は Opus にし、件数の多いほかの分野は Sonnet にした

- **やったこと**: 工程5の記録の数字と引用を会議録の原文と、工程6・7のまとめの数字と引用を引いた記録と、コードで照合した。確かめられなかった文に「［要確認］」の印を付け、一覧を `topics/要確認.md` に出した。細かく分けた5分野の README の［要確認］121文は、人が原文で1文ずつ確かめ、直すべき20文を直した。作りと結果の詳しいことは [照合と手直し.md](照合と手直し.md)

  - 照合の結果（`verify/`）は Git に入れる。README を作り直すときに印を付けるのに使うので、原文（`data/`）のないクローンでも印が消えないように

- **かかった時間**: 照合は1分ほど

## やってみてわかったこと

- **Haiku の出力の上限**: Haiku は考える過程が長く、出力の上限16,000トークンでは代表質問40件のうち31件が途中で切れた。上限を64,000にすると切れなかった（使わなければ課金されない）
- **日本語のトークン数**: 会議録の本文は1字がおよそ0.89トークン、出力は本文1字あたり0.36トークンだった。工程6の入力は、記録の番号や見出しが付くので1字あたり約1.1トークンになった。見積もりはこの値を使う
- **少ない試行では失敗率は読めない**: 工程6の試行で Sonnet が崩れたのは7組のうち1組だけだったが、本番では約3割が形式チェックに落ちた。形式チェックと自動の送り直し、上のモデルでの流し直しを、最初から用意しておくとよい
- **形式チェックのしきい値**: 「出典のない文」は最初5%にしたが、書き出しの1〜3文（「この時期の論点は〜だった。」）にも当たって半分近くが落ちたので、1割に緩めた。「同じ文の繰り返し」は最初3回にしたが、3つの会派がそれぞれ「陳情第13号は不採択とすべきだと主張した。」と書いた正しいまとめが落ちたので、5回にした
- **バッチの失敗の数え方**: 途中で API のクレジットが切れ、バッチが失敗して本番が15分ほど止まった。足してから同じコマンドで続きを流せた。クレジット不足のようなバッチ側の失敗を「2回落ちたら上のモデル」の回数に数えると、止まった分がすべて上のモデルに回るので、数えないようにした
- **照合の拾いすぎ**: 機械的な照合は拾いすぎる。任期の区切りの年（「2015〜2019年は…」の2019）、月の幅（「2〜3月」の2）、「第6波」の6、会議録の範囲の注記など。細かく分けた5分野の README の［要確認］121文を人が確かめると、中身が誤っていたのは8文で、65文は照合の拾いすぎだった。決まった形は照合で拾わないようにした
- **数字の書き方のずれ**: 原文は全角数字、記録は半角数字のことが多い。全角・半角、カンマ、「．」「％」をそろえる前は、記録の数字の約9%が「原文にない」と出た
- **記録の引用は原文と少し違う**: 工程5で Haiku が写した引用は、語順や読点が原文と少し違うことがある。まとめの引用を原文どおりに直すと、今度は記録と合わなくなる。そこで、引用と2桁以上の数字は、引いた記録のまとまりの会議録の原文にあれば確かめられたものとした
- **AI が作ったものを手で直さない**: 直しを別のファイルに書いて当てる形にしたので、流し直しても直しが消えない。最初は「直す前の文字列があれば当てる」にしていて、直した後の文字列が直す前の文字列を含む2件が、2回流すと二重に当たった。「直した後の文字列がもうあれば飛ばす」に変えた
- **Windows の改行**: Windows で `core.autocrlf=true` のままクローンすると改行が CRLF になり、`--render` で作り直すと、中身は同じでも数百のファイルが「変更あり」に見える。`.gitattributes` に `* text=auto eol=lf` を書いて LF にそろえた
- **日本語のフォルダ名**: Git は既定で日本語のファイル名を `"\346\227\245..."` のように表示する。`git config core.quotepath false` にすると読める。`git subtree split` で日本語のフォルダを切り出すときは、これを付けないと失敗した
- **クローンしたばかりの状態で確かめる**: 手元では動いても、`data/` のないクローンでは動かないものがあった。照合の結果を `data/` に置いていたので README を作り直すと印がすべて消えた、API を呼ばない `--render` でも SDK を読んでいて `npm install` なしでは落ちた、など。新しくクローンして手順どおりに流して見つけ、直した
- **GitHub の画面で表示できる大きさ**: 最初は「1MB 未満なら開ける」として区のファイルを分けたが、公開して確かめると、大きいファイルは Markdown として描画されなかった（ページの `richTextTruncated` が true になる）。上限はバイト数だけでは決まらず、相対リンクの多いファイルほど早く当たる（描画後の HTML の大きさで決まるとみられる）。話題の年表（1件1KB ほどにリンク1本）は 396,488バイトでも表示されたが、地名の一覧（1件150バイトほどにリンク1本）は 257,855バイトで表示され、36万バイト前後で表示されなかった。話題の年表は36万バイト、地名の一覧は24万バイトまでにして分け直し、公開した画面で確かめた。全市の年表は、ほとんどがこの大きさを超えるので入れていない
