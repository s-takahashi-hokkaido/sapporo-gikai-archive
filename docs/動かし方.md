# 動かし方

手元に写して、区の入口や年表を作り直す、新しい会議の分を足す、ための手順。工程ごとの判断と理由は [作り方.md](作り方.md)、全体の流れは [docs/README.md](README.md) にある。コマンドはリポジトリの直下で実行する。

## 1. 手元に写す

[Git](https://git-scm.com/) と [Node.js](https://nodejs.org/)（18以上）を入れておく。

```bash
git clone https://github.com/s-takahashi-hokkaido/sapporo-gikai-archive.git
cd sapporo-gikai-archive
git config core.quotepath false   # 日本語のファイル名を読める形で表示する
```

改行は `.gitattributes` で LF にそろえてある。Windows でも、作り直したあと中身が同じなら「変更あり」にならない。

## 2. 区の入口を作り直す（AI は使わない。料金なし）

```bash
node pipeline/09_area.mjs --all            # 10区すべてと、10区の一覧 areas/README.md（数秒）
node pipeline/09_area.mjs --area 東区      # 1つの区だけ（数秒）
node pipeline/09_area.mjs --list           # 区ごとの記録の数を見る（何も書かない）
node pipeline/07_history.mjs --render      # 話題の一覧（topics/README.md）の区へのリンクを作り直す
```

区の名前は「中央区、北区、東区、白石区、厚別区、豊平区、清田区、南区、西区、手稲区」のどれかを「区」まで書く。区のフォルダは消してから書き直す。GitHub の画面で Markdown として表示できる大きさを超えるファイルは、`地名.md`、`地名2.md`… のように自動で分ける（大きさの見積もり方は [作り方.md](作り方.md) の「やってみてわかったこと」）。

## 3. 全市の年表を作る（AI は使わない。料金なし）

```bash
node pipeline/07a_timeline.mjs             # topics/<話題>/年表.md を作る（数秒、計約100MB）
```

工程5の記録を話題ごとに日付順に並べたもの。副の話題として付いた記録も「（副）」として載る。Git には入れない（`.gitignore`）。話題の一覧や話題の README からはリンクしていないので、エディタで `topics/<話題>/年表.md` を開いて読む。

## 4. 新しい会議の分を足す（年に1回ほど。API の料金がかかる）

会議録検索システムに新しい会議が載ったら（2026年の第3回定例会以降は2027年の初めごろ）、次の順に流す。Anthropic の API キーが要る。API の料金がかかる工程は、先に `--dry-run` で量を出して見積もる（スクリプトの頭に単価の表がある）。

クローンしたばかりで `data/` がないときは、先にすべての年の原本を取る（`node pipeline/01_download.mjs`。約3,500件、2時間前後。料金なし）。会議録の原本と途中の生成物（計1GB 近く）は Git に入っておらず、照合（工程8）は会議録の原文と突き合わせるので、すべての年の分が要る。原文がない年があると `08_verify.mjs` は止まる。`.env.example` を `.env` に写し、`ANTHROPIC_API_KEY=` の後ろにキーを書く（`.env` は Git に入らない）。

```bash
npm install                                               # 初回だけ（API を呼ぶ工程5〜7で使う）
node pipeline/01_download.mjs --from 2026 --to 2027       # 会議録の原本を取る（1.5秒に1件。並列にしない）
node pipeline/02_to_markdown.mjs                          # Markdown にする
node pipeline/03a_speeches.mjs && node pipeline/03b_toc.mjs && node pipeline/03c_members.mjs && node pipeline/03d_plenary.mjs && node pipeline/03e_committee.mjs && node pipeline/03f_summary.mjs   # 発言に分け、質問者ごとのまとまりにする
node pipeline/05_classify.mjs --year 2026 --dry-run       # 送る件数と量を見て見積もる
node pipeline/05_run_all.mjs --from 2026 --to 2027 --retries 2   # 増えた分を AI で分類・要約する
```

そのあと、いちばん新しい任期のまとめを作り直す（`bundles/<話題>/2023-2027.json` と `parts/` の該当するもの、`topics/<話題>/history.json` を消してから流す）。

```bash
node pipeline/06_bundle.mjs --pillars --dry-run           # 送る件数と量を見て見積もる（--others、07 も同じ）
node --env-file=.env pipeline/06_bundle.mjs --pillars     # 細かく分けた5分野の話題×任期（Opus）
node --env-file=.env pipeline/06_bundle.mjs --others      # ほかの話題×任期（Sonnet）
node --env-file=.env pipeline/07_history.mjs --pillars    # 20年のまとめ（Opus）
node --env-file=.env pipeline/07_history.mjs --others
node pipeline/07b_fix.mjs                                 # 人が直した文を当て直す
node pipeline/08_verify.mjs                               # 照合する
node pipeline/07_history.mjs --render && node pipeline/06_bundle.mjs --render   # 照合の印を付ける
node pipeline/09_area.mjs --all                           # 区の入口を作り直す
```

会議録の範囲の注記（「2026年6月ごろの分まで」）は、README.md、`09_area.mjs`、工程7の指示書、`08_verify.mjs`（照合で拾わない決まり）に書いてある。足したら直す（指示書を直すときは版を上げる。[AGENTS.md](../AGENTS.md)）。

## 5. AI に頼む

Claude Code でも Codex でも、このフォルダを開いて頼めば、[AGENTS.md](../AGENTS.md) の決まりに沿って作業する（Claude Code は `CLAUDE.md` から `AGENTS.md` を読む）。たとえば次のように頼む。

- 「区の入口を作り直して」
- 「2026年の第3回定例会以降を足したい。料金の見積もりから」
- 「除排雪の体制と費用の README の［要確認］を原文で確かめて」

API の料金がかかる工程は、流す前に見積もりを出して確かめるよう AGENTS.md に書いてある。

## 工程ごとのコマンド

### 工程1 原本の取得

```bash
node pipeline/01_download.mjs --from 2025 --to 2025 --kinds 1   # お試し: 2025年の定例会だけ（30件ほど、1分くらい）
node pipeline/01_download.mjs                                   # 2007〜今年の定例会・臨時会・委員会すべて（約3,500件、2時間前後）
```

一括だと長いので、6回に分けて流すとよい（1回20分前後）。

```bash
node pipeline/01_download.mjs --kinds 1,2                      # 定例会・臨時会（全20年、約600件）
node pipeline/01_download.mjs --kinds 3 --from 2023 --to 2026  # 委員会を4年ずつ、新しい年から
node pipeline/01_download.mjs --kinds 3 --from 2019 --to 2022
node pipeline/01_download.mjs --kinds 3 --from 2015 --to 2018
node pipeline/01_download.mjs --kinds 3 --from 2011 --to 2014
node pipeline/01_download.mjs --kinds 3 --from 2007 --to 2010
```

- 途中で止めても（Ctrl+C）、もう一度実行すれば取得済みのファイルを飛ばして続きから再開する
- リクエストは1.5秒に1回。相手のサーバーに負荷をかけないため、間隔を縮めない・並列で動かさない
- 終わったら最後の行の「失敗」「要確認」を見る。失敗分はもう一度実行すれば取り直す
- 目録（`manifest/`）は、その年のその種別を最後まで取り終えたときに書かれる
- どこまで取れたかは年ごとのファイル数で確かめる（1年分の目安は、定例会と臨時会で約30件、委員会まで含めて約180件）

### 工程2 Markdown への変換

```bash
node pipeline/02_to_markdown.mjs           # まだ変換していない原本だけ変換する（数秒）
node pipeline/02_to_markdown.mjs --force   # すべて変換し直す（スクリプトを直したとき）
```

- ダウンロードの途中でも動かせる。もう一度実行すれば増えた分だけ変換する
- 最後に「原本と内容が一致しない」「文字化け」「発言数が目録と違う」の件数を出す。0件でなければ変換を見直す

### 工程3 構造化

```bash
node pipeline/03a_speeches.mjs   # T1: 発言の層を作る（数秒）
node pipeline/03b_toc.mjs        # T2: 目次を読む（1秒）
node pipeline/03c_members.mjs    # T3: 会派の名簿（pipeline/members/*.csv）を確かめる（数秒）
node pipeline/03d_plenary.mjs    # T4: 本会議のまとまりを作る（数秒）
node pipeline/03d_plenary.mjs --show 2024/2024-02-20_k1_4349.md     # 1日分のまとまりを一覧にして見る（抜き取りの確認用）
node pipeline/03e_committee.mjs  # T5: 委員会のまとまりを作る（数秒）
node pipeline/03e_committee.mjs --show 2016/2016-02-29_k3_3178.md   # 1日分のまとまりを一覧にして見る
node pipeline/03f_summary.mjs    # T6: まとまりを合わせて数え、本会議と委員会をまたいで確かめる（何も書き出さない）
```

- 上の順番（`03a` → `03b` → `03c` → `03d` → `03e` → `03f`）で流す。どれも何度流しても同じ結果になる。全部で15秒ほど
- 原本を取り直したときや、名簿の CSV を直したときに流す
- 各スクリプトは最後に確かめの件数を出す。0件でなければ見直すもの、0件でなくてよいもの（（参考）（確認用）の付いたもの）の見分け方は [工程3の設計.md](工程3の設計.md)
- 会派の名簿の本体は `pipeline/members/` の3つの CSV で、手で直す。直したら `03c_members.mjs` を流して、検証の件数が0件のままかを見る
- 名簿の版を取り直すとき（年に1回くらい、または会派が変わったと聞いたとき）は `node pipeline/03c_members.mjs --fetch`。Wayback へのリクエストは3秒に1回
- 名簿を根拠から作り直したいときは `node pipeline/03c_members.mjs --draft` で `data/struct/members_draft.csv` を作り、`members.csv` と見比べて写す（`members.csv` は上書きしない）

### 工程4 話題の一覧

```bash
node pipeline/04a_material.mjs                  # 材料を取り出す（数秒）
node pipeline/05_classify.mjs --trial --dry-run # API を呼ばずに、送る件数と量を確かめる
node --env-file=.env pipeline/05_classify.mjs --trial --probe 243540   # 1件だけバッチを使わずに送って結果を見る（何も書かない）
node --env-file=.env pipeline/05_classify.mjs --trial --model claude-opus-5-5   # 300件を分類する（バッチ）。結果は data/topics/trial/<モデル>/
node pipeline/04b_trial_report.mjs              # 試行の結果を集計する
node --env-file=.env pipeline/05_classify.mjs --trial --tag v3   # 同じ300件を別のモデル・指示書で分類する（既定は Haiku）
node pipeline/04c_compare_models.mjs claude-haiku-5-5-v3   # Opus と比べる（引数はフォルダ名）
```

- 試行の300件は、乱数の種を固定して抜くので毎回同じになる
- 一覧を直すときは `topics.csv` を直すだけでよい（指示書は流すときに一覧を差し込む）。ただし工程5から流し直しになる
- 指示書そのものを直すときは `prompts/05_classify_v4.md` のように版を上げ、`05_classify.mjs` の `PROMPT_VERSION` を変える。記録には指示書の版が残る

### 工程5 分類・要約

```bash
node pipeline/05_classify.mjs --year 2024 --dry-run         # API を呼ばずに、送る件数と量を確かめる
node pipeline/05_run_all.mjs --retries 2                    # 2007〜2026年をすべて流す（年ごとにバッチ。失敗の残る年は2回まで送り直す）
node pipeline/05_run_all.mjs --from 2026 --to 2026          # 年を絞る
node --env-file=.env pipeline/05_classify.mjs --year 2024   # 1年だけ流す
```

- 既定は Haiku 5.5、指示書 v3、effort medium、出力の上限64,000
- 記録済みのまとまりは飛ばすので、何度流してもよい
- 何度送り直しても同じところで落ちるものは、`--model claude-sonnet-5-5` を付けてその年だけ流すと通る
- 指示書や一覧を直して全部やり直すときは、`records/` の該当する年のファイルを消してから流す

### 工程6 話題×任期のまとめ

```bash
node pipeline/06_bundle.mjs --list                          # 話題×任期ごとの記録の数と量（時期に分ける組がわかる）
node pipeline/06_bundle.mjs --pillars --dry-run             # API を呼ばずに、送る件数と量を確かめる
node --env-file=.env pipeline/06_bundle.mjs --pillars       # 細かく分けた5分野の話題（125組。既定は Opus 5.5）
node --env-file=.env pipeline/06_bundle.mjs --others        # ほかの分野の話題（140組。既定は Sonnet 5.5）
node --env-file=.env pipeline/06_bundle.mjs --topic 地下鉄  # 1つの話題だけ（先に bundles/<話題>/ の該当する任期を消す）
node --env-file=.env pipeline/06_bundle.mjs --collect <batch_id>   # 途中で止めたとき、そのバッチの結果を取って続ける
node pipeline/06_bundle.mjs --render                        # API を呼ばずに .md だけ作り直す（照合の印を付け直す）

# 試行（モデルを比べる）
node --env-file=.env pipeline/06_bundle.mjs --trial --model claude-haiku-5-5   # 決まった7組をまとめる → data/bundle/trial/<モデル>/
node pipeline/06b_compare_bundle.mjs                        # モデルごとに比べる → data/bundle/trial/compare.md、side/
```

- `--pillars` は `topics.csv` の「柱」の列に値がある話題（細かく分けた5分野）
- まとめ済みの組は飛ばすので、何度流してもよい。流し直すときは `bundles/<話題>/<任期>.json`（と `parts/` の該当するもの）を消す
- 量の多い組は2回のバッチに分かれ、スクリプトは1回目が終わると2回目を自動で送る

### 工程7 20年のまとめ

```bash
node pipeline/07_history.mjs --pillars --dry-run              # 送る話題と量を確かめる
node --env-file=.env pipeline/07_history.mjs --probe --topic 地下鉄   # 1つだけバッチを使わずに送って結果を見る（何も書かない）
node --env-file=.env pipeline/07_history.mjs --pillars        # 細かく分けた5分野の話題（25）
node --env-file=.env pipeline/07_history.mjs --others         # ほかの分野の話題（28）
node --env-file=.env pipeline/07_history.mjs --topic 地下鉄   # 1つの話題だけ（作り直すときは topics/地下鉄/history.json を消す）
node pipeline/07_history.mjs --render                         # API を呼ばずに README と話題の一覧だけ作り直す
```

- 工程6のまとめがそろっていない話題は飛ばす。工程6が終わってから流す
- 流し直したら、下の手直しをもう一度当てる

### 手直し（工程7のあと）

```bash
node pipeline/07b_fix.mjs                # pipeline/fixes/07_history.jsonl の直しを history.json に当てる（何度流してもよい）
node pipeline/08_verify.mjs              # 照合し直す
node pipeline/07_history.mjs --render    # README を作り直す（照合の印を付け直す）
node pipeline/06_bundle.mjs --render     # 任期ごとのまとめの .md も印を付け直す
```

- 直す前の文字列（`before`）は、その話題のまとめで1か所にだけ出るものにする。見つからない・2か所以上にあるときは止まる
- 書き方は [照合と手直し.md](照合と手直し.md) の「人の手直し」

### 工程8 照合

```bash
node pipeline/08_verify.mjs              # 照合して topics/要確認.md と verify/ に書く（1分ほど。data/struct/ の原文がないと止まる）
node pipeline/07_history.mjs --render    # README の［要確認］の印を付け直す
node pipeline/06_bundle.mjs --render     # 任期ごとのまとめの印を付け直す
```

- 工程6・7のまとめや記録を作り直したら、もう一度流す
- 照合のやり方は [照合と手直し.md](照合と手直し.md)

## ファイル構成

| 場所 | 内容 | Git |
|---|---|---|
| `README.md` | 読む人の入口 | 入れる |
| `LICENSE` | プログラム（MIT）のライセンス | 入れる |
| `AGENTS.md`、`CLAUDE.md` | AI のエージェント向けの決まり。本体は `AGENTS.md`（Codex が読む）で、`CLAUDE.md` は `@AGENTS.md` の1行（Claude Code が読む） | 入れる |
| `docs/` | エンジニア向けの資料（この資料、[作り方](作り方.md)、[工程3の設計](工程3の設計.md)、[照合と手直し](照合と手直し.md)） | 入れる |
| `topics/README.md` | 話題の一覧（分野、話題、記録の数、20年のまとめへのリンク） | 入れる |
| `topics/<話題>/README.md` | 話題ごとの20年のまとめ。現状、20年の経緯、会派ごとの立場、市の答弁の変化、未解決の論点。日付は会議録へのリンク | 入れる |
| `topics/<話題>/history.json` | 工程7のまとめ（出典を記録の id で持つ。モデル、トークン数も）。README はここから作る | 入れる |
| `topics/<話題>/年表.md` | 全市の年表（上の「3」） | 入れない（53話題で約100MB） |
| `topics/要確認.md` | 照合で、数字や引用を引いた記録や原文で確かめられなかった文の一覧 | 入れる |
| `topics/errors.jsonl` | 工程7で形式チェックに落ちたものの控え（落ちたものがあるときだけできる。いまはない） | 入れる |
| `areas/README.md` | 10区の一覧 | 入れる |
| `areas/<区>/README.md` | 区の入口（話題ごとの件数、最近の記録、20年の経緯へのリンク） | 入れる |
| `areas/<区>/<話題>.md`、`地名.md` | その区の記録の、話題ごとの年表と、地名ごとの一覧（GitHub の画面で表示できる大きさを超えるものは `地名2.md` などに分ける） | 入れる |
| `bundles/<話題>/<任期>.json`、`.md` | 工程6のまとめ（この4年の要点、主な動き、会派ごとの主張、市の答弁の変化、残っている論点）。`.json` は出典を記録の id で持ち、`.md` は id を会議録へのリンク（日付）にした読む用 | 入れる |
| `bundles/<話題>/parts/` | 量の多い組を時期に分けてまとめたもの（1つにまとめ直す前） | 入れる |
| `bundles/errors.jsonl` | 工程6で形式チェックに落ちたもの、バッチの失敗の控え（送り直した回数をここから数える） | 入れる |
| `records/<年>.jsonl` | 工程5の記録の本体。1つの項目が1行（話題、副の話題、地域、地名、質問と答弁の要旨、数字、約束、発言の HUID、出典の URL、モデル、指示書の版） | 入れる |
| `records/empty/<年>.jsonl` | 手続きだけで項目のなかったまとまり。送り直さないための控え | 入れる |
| `records/errors/<年>.jsonl` | 形式チェックに落ちたもの、拒否されたものの控え。もう一度流せば送り直す | 入れる |
| `verify/` | 照合の結果（`records.jsonl` は記録と原文の食い違い、`summaries.jsonl` はまとめの要確認）。`--render` が `summaries.jsonl` を読んで印を付ける | 入れる |
| `pipeline/01_download.mjs`〜`09_area.mjs` | 工程ごとのスクリプト（上の「工程ごとのコマンド」）。使い方は各ファイルの頭のコメントにもある | 入れる |
| `pipeline/lib.mjs` | 工程3以降で共有する関数（氏名の正規化、任期、会期、委員会名、発言単位の閲覧 URL、会派の名簿の引き方） | 入れる |
| `pipeline/topics.csv` | 話題の一覧（話題、柱、分野、範囲、分け目、材料の例）。工程5の AI はこの中から選ぶ。「柱」の列は細かく分けた5分野の名前 | 入れる（手で直す） |
| `pipeline/members/members.csv` | 会派の名簿。任期×氏名ごとに、会派・期間・選出区・根拠（2003〜2027年の6任期） | 入れる（手で直す） |
| `pipeline/members/factions.csv` | 会派の正式名と、会議録での呼び方（略称・旧称）、あった任期、名前だけ変えた会派の系列（`lineage`） | 入れる（手で直す） |
| `pipeline/members/aliases.csv` | 氏名の表記ゆれ・誤字と、名簿の氏名 | 入れる（手で直す） |
| `pipeline/prompts/` | 工程5〜7の指示書。いま使う版は `05_classify_v3`、`06_bundle_v2`、`07_history_v2`。直すときは版を上げて別のファイルにする | 入れる |
| `pipeline/fixes/07_history.jsonl` | 人が原文で確かめて直した文。1行1件（話題、直す前、直した後、理由、日付） | 入れる（手で直す） |
| `package.json`、`package-lock.json` | 工程5〜7で使う Anthropic の SDK（`npm install` で `node_modules/` に入る） | 入れる（`node_modules/` は入れない） |
| `.env.example` | API キーの雛形。`.env` に写してキーを書く | 入れる |
| `.env` | API キー（`ANTHROPIC_API_KEY`） | 入れない |
| `.gitattributes` | 改行を LF にそろえる | 入れる |
| `data/raw/` | 会議録の原本（1日分の会議が1ファイル、Shift_JIS の HTML のまま）と目録 | 入れない |
| `data/md/` | 会議録の Markdown（UTF-8）。原文を読むときはこちら | 入れない |
| `data/struct/` | 工程3の出力。発言（`speeches/<年>.jsonl`。1つの HUID が1行）、会議の目録、目次、まとまり（`exchanges/`）、会派の根拠 | 入れない |
| `data/` のほか | 試行の結果、バッチの控え、比べ合わせ など | 入れない |

`data/` は容量が大きく（計1GB 近く）、もう一度ダウンロード・変換すれば作り直せるので Git に入れない。
